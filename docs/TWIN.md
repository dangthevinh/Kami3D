# The 3D twin (Phase D7)

`/data2map/twin` is the Data2Map module in three dimensions: the city as OpenStreetMap records it,
extruded from its own building heights over real elevation, with the D4 delivery sample moving
through it on a stream from Postgres.

## The engine decision, recorded so it is not re-litigated

D7 was written after looking at 图扑软件 (HighTopo)'s port and warehouse "digital twin" demos. The
engine behind them is **HT for Web**: a self-developed, **closed-source WebGL library sold under a
commercial licence**. Its core is a single `ht.js` of roughly a megabyte loaded with a script tag,
3D scenes are built with `new ht.graph3d.Graph3dView()`, and the published learning material says it
plainly: *"not open source and requires a commercial license to use"*, with a trial package on
request.

That fails this project twice: a fresh clone would need a licence, and a one-megabyte monolith cannot
be cut per route to fit a bundle budget. So the **composition** was adopted and the engine refused.
HT for Web is four products in one, and every piece has an open-source substitute - most of which
this stack already had:

| Piece of HT for Web | Open-source substitute | Licence | Used here |
| --- | --- | --- | --- |
| 3D scene engine | three.js + @react-three/fiber | MIT | already in the stack (model viewer) |
| WebGIS 3D | MapLibre GL JS + `fill-extrusion` + `setTerrain` | BSD-3-Clause | **this page** |
| 3D Tiles / globe | CesiumJS, 3d-tiles-renderer | Apache-2.0 | recorded, not adopted: needs a tileset and a route budget of its own |
| BIM / IFC | web-ifc + @thatopen/components | MPL-2.0 + MIT | available for an IFC upload; nothing to show yet |
| Chart and gauge library | Apache ECharts, or the components this project already writes | Apache-2.0 | `components/stats/*` — ECharts only if a measurement ever says it is needed |
| Push pipeline | Supabase Realtime | — | **this page** |
| Self-hosted IoT path | EMQX / Mosquitto + Node-RED, or Eclipse Ditto / ThingsBoard | *read the LICENSE first / EPL-2.0 / Apache-2.0* | recorded for the day there is hardware |
| Ops dashboard | Grafana | AGPL-3.0 | internal only, never bundled |

Two licences were refused rather than adopted: **xeokit-sdk** (AGPL-3.0, and it would be embedded in
a page) and any 3D Tiles service that needs an account (Cesium ion, Google). The AGPL line is about
where the code ends up, not about the licence being wrong: Grafana as an internal tool is fine,
Grafana inside the bundle would not be.

## What is real, and what is simulated

| Layer | Source | Real? |
| --- | --- | --- |
| Buildings | OpenStreetMap footprints, extruded with the `render_height` field OpenMapTiles ships (via OpenFreeMap's keyless vector tiles) | **real**, ODbL 1.0 |
| Terrain | AWS open terrain tiles (`elevation-tiles-prod/terrarium`) | **real**, public-domain sources (SRTM and friends) |
| Routes, stops, coverage bands | the D4 sample, generated by this project | simulated, CC0 |
| Vehicles and their positions | `public.vehicle_positions`, written by the simulator | simulated, CC0 — and the table enforces it |
| Deliveries and their timing | derived from the positions and the sample's windows | simulated |

Not every building carries a height, and the ones that do not are drawn at the lowest class rather
than hidden or turned into towers: a city centre that renders as empty looks like a bug, and a
skyline where every unknown became a tower is a fabrication. `buildingClassFor` returns `null` for a
missing height, and the check suite pins that.

## The pipeline

```
scripts/simulate-fleet.mjs ──▶ public.vehicle_positions ──▶ Supabase Realtime ──▶ the page
        │                              │
        │                              └── prune_vehicle_positions(168)   hourly, retention
        └── rollup_vehicle_kpi_hours(24) ──▶ public.logistics_kpi_hourly ──▶ the cockpit's bars
```

| Object | What it is for |
| --- | --- |
| `vehicle_positions` | one row per simulated push; `source` and `synthetic` are pinned by CHECK constraints so a real feed cannot be written here by accident |
| `logistics_kpi_hourly` | the same arithmetic the cockpit does, executed in SQL and upserted per hour and vehicle |
| `prune_vehicle_positions(keep_hours)` | retention, default 168 hours, refusing a non-positive window |
| `rollup_vehicle_kpi_hours(since_hours)` | the rollup that fills the table above |
| `haversine_km(...)` | the **same** formula as `lib/geo.ts`, so the SQL and the page cannot disagree |

**The reader cannot write.** There is no insert, update or delete policy on either table, `revoke all`
is followed by `grant select` for `anon` and `authenticated`, and the two functions are executable by
`service_role` only. Verified against the live project: an anonymous insert answers `401`, an
anonymous `prune` call answers `401`, and `prune_vehicle_positions(0)` raises.

## Running it

```bash
npm run db:schema                      # the tables, policies, functions and the publication
npm run fleet:simulate -- --once       # one sample per vehicle, now
npm run fleet:simulate -- --backfill 120   # two hours of history, one sample a minute, then a rollup
npm run fleet:simulate -- --loop --interval 5   # keep pushing, for the live page
npm run fleet:simulate -- --rollup     # refresh the hourly table
npm run fleet:simulate -- --prune      # retention sweep
npm run fleet:simulate -- --status     # what the two tables hold
npm run fleet:verify                   # subscribe as anon, run the simulator, expect the events
npm run check:twin                     # the pure rules, the cockpit arithmetic and the SQL guards
```

`fleet:verify` is the end-to-end proof and it needs the network, which is why it is not part of
`check:suites`: it subscribes to the same channel with the same anonymous key the browser uses, runs
the simulator, waits for the inserts, and then confirms that the same key cannot write.

## Why the twin is not a registry product

The Data2Map registry (`data2map_datasets`, `data2map_layers`) describes the **five products** D2-D6,
and `scripts/check-data2map.mjs` asserts that a product claiming to be live has a page and that every
referenced dataset exists. The twin is a page of the module that draws two basemap-derived layers and
one stream rather than a product with its own datasets, so its four layers are declared next to the
code that draws them (`TWIN_LAYERS` in `lib/data2map/twin.ts`) and still carry a source and a licence
for the panel to print. If the twin ever grows datasets of its own, they belong in the registry.

## Limits worth knowing before reading the page

- **Three dimensions need WebGL.** The headless browser used for verification has none, so the local
  checks cover the server render, the stream, the SQL and the pure rules - not the pixels. The map
  falls back to `MapFallback` and the page still renders, and the stream is verified from Node.
- **Terrain is off on small screens** (one download, and the delta is flat). It can be switched on in
  the panel, from any size.
- **Extrusion starts at zoom 14.** Below that a city of boxes is a grey smear; the flat map is better.
- **The fleet is a script, not a service.** `scripts/simulate-fleet.mjs` plays the part a fleet
  management system would play: it computes where each van should be from the routes this project
  generated and pushes a row. The production path - MQTT from the vehicles, a worker, the same table
  - is recorded above so nobody has to design it twice.
